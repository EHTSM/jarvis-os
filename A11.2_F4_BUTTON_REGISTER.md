# A.11.2 — F4: Button System Final Assessment

**Mission rule:** do not attempt a mass migration; merge only where an existing
canonical mechanism, identical semantics, safe visual equivalence and no
behavioural risk all hold; otherwise classify as a gap with exact scope.

**Result: GAP — DESIGN-SYSTEM CONSOLIDATION. Zero systems merged.**

---

## Canonical primitive — exists

`index.css` defines `.btn`, `.btn--primary`, `.btn--success`, `.btn--danger`,
`.btn--sm`, `.btn--xs` and `.btn:disabled` (which dims the *surface*, not the
label). Recovered in B19.2.2, where those classes were applied in JSX but
defined in **no** stylesheet.

The 71 namespaced systems predate it.

---

## Classification against the merge test

A system may only be merged if **all four** hold: canonical mechanism exists ✓,
identical semantics, safe visual equivalence, no behavioural risk.

| Group | Count | Merge test | Outcome |
|---|---:|---|---|
| **Intentionally specialised** | ~46 | fails *identical semantics* | keep |
| **Namespace-only variants** | ~12 | fails *safe visual equivalence* (21 paddings, 8 radii — no single correct target) | keep |
| **Unused** | 1 | no consumer to migrate | leave in place |
| **Genuine duplicates** | **0** | — | none found |

### Evidence that specialisation is real, not accidental

| System | Job it does that `.btn` does not |
|---|---|
| `.cmd-chip` | member of a horizontally scrolling dispatch row |
| `.pv2-btn--wa` | WhatsApp send affordance |
| `.gaf-filter-btn` | carries an inline count badge |
| `.cv2-filter-btn` | active-state ring for contact filters |
| `.dv2-btn--xs` | deliberately 11px for dense DevOps rows |
| `.op-send-btn--ready` | operator-console readiness state |

Merging any of these would change interaction semantics or visual design —
both explicitly forbidden.

---

## Why no partial merge was attempted

The 12 "namespace-only" candidates look mergeable but are not **safe**: they
span 21 distinct paddings. Picking one means changing 11 surfaces' visual
density — a design decision without a canonical answer, taken outside a
design-system phase. The mission forbids changing visual design merely because
two components differ.

---

## Exact migration scope (for the phase that takes it on)

| Dimension | Value |
|---|---|
| **Files** | 59 CSS files declaring a `-btn` system |
| **Components** | 58 live systems across ~58 surfaces |
| **Variants** | primary / secondary / destructive / ghost / icon / sm / xs per system |
| **Migration units** | ~58 (one per system) + ~46 specialisation carve-outs to preserve |
| **Risk** | HIGH — every unit touches shipping UI on a live surface |
| **Dependencies** | `.btn` base in `index.css`; the `--radius-sm` / `--radius-pill` scale; `--on-*` label tokens |
| **Sequencing** | start with the **12** systems already referencing `var(--radius-sm)` — closest to canonical |
| **Measurable target** | live button-height histogram: drive top-5 coverage above its current **57 %**; treat any increase in distinct heights as a regression |
| **Out of scope** | the 6 specialised systems tabled above |

**Classification: GAP — DESIGN-SYSTEM CONSOLIDATION.** No Button V2 was created.
