# A.11.2 — F3: API Error Path Recovery

**Scope:** the **15** category-C paths A.11.1 classified as user-visible
mutations whose failure was invisible. The other 543 empty catches were **not**
touched, per the mission rule.

**Result: 15 / 15 FIXED — category C is now 0.**

---

## Method per site

1. Reproduce the swallow (read the call, confirm the catch discards).
2. Identify the error mechanism **already present in that file**.
3. Reuse it — no new notification framework.
4. Preserve the real backend semantics.
5. Rebuild and re-measure.

---

## Root cause found while recovering

Four files shared a private helper that returned `r.json()` with **no status
check**:

```js
const API = async (method, path, body) => {
  const r = await fetch(`/api${path}`, { … });
  return r.json();          // ← a 403 body flows through as DATA
};
```

So the caller's `catch` only fired on a network error; a real 4xx/5xx arrived as
a normal value. **Same defect class as A.11 F1.**

Recovered to mirror the canonical `_client.js` semantics — preserve the
backend's own message, attach the status, throw:

```js
if (!r.ok) {
  const err = await r.json().catch(() => ({}));
  const e = new Error(err.error || err.message || `HTTP ${r.status}`);
  e.status = r.status;
  throw e;
}
```

Applied in `AutonomousPlatformPanel`, `RepositoryMapPanel`,
`EngineeringMemoryPanel`, `SelfImprovementPanel`.
