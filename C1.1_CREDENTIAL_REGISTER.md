## CORRECTION — C.1 overstated the credential gap

C.1 reported **8 missing credentials**, including `WHATSAPP_TOKEN` and `TELEGRAM_BOT_TOKEN`. Both were wrong: I probed **invented variable names** rather than the names the code reads.

| Capability | C.1 claimed | Reality | Actual variable |
|---|---|---|---|
| WhatsApp | `WHATSAPP_TOKEN` MISSING | **PROVISIONED** | `WA_TOKEN` + `WA_PHONE_ID` |
| Telegram | `TELEGRAM_BOT_TOKEN` MISSING | **PROVISIONED** | `TELEGRAM_TOKEN` |

Confirmed live: `/telegram/status` → `{"configured":true}`; `/settings/status` → `whatsapp.hasToken: true` (reads `process.env.WA_TOKEN`).

**Lesson:** checking a plausible variable name proves nothing. Verify against the name the code reads.

## Are the gaps reported honestly by the product?

A credential gap is only acceptable if the surface **admits** it rather than silently pretending to work.

| Surface | Response | Honest? |
|---|---|---|
| `/push/readiness` | `{"pushReady":false,"detail":"FIREBASE_PROJECT_ID not set"}` | ✅ **Names the exact missing variable** |
| `/telegram/status` | `{"configured":true}` | ✅ Accurate — genuinely provisioned |
| `/settings/status` | `whatsapp.hasToken:true, source:"env"` | ✅ Accurate |
| `/wiring/ai` | per-provider `checks[]` with pass/fail | ✅ Per-key truth |
| `/co2/ai-providers` | lists `envKey` + `signupUrl` per provider | ✅ Actionable |

**No surface was found falsely claiming an unconfigured integration was ready.** This is a genuine strength: the platform's credential reporting is truthful.

One inconsistency: `/push/readiness` returns `firebaseStatus:"READY"` while `pushReady:false` and `detail` names the missing variable. The composite verdict is correct; the `firebaseStatus` sub-field is misleading. Minor; not fixed in this phase (out of scope — no new capability).

## Impact per capability

### Sentry — `SENTRY_DSN` **(highest operational risk)**
`sentryService.cjs` (198 LOC) is fully built and wired; `isConfigured()` returns false, so it correctly no-ops. **Production has no crash reporting.** Pure provisioning decision — zero code work.

### Email / SMTP — **all five transport variables unset**
`/growth/email/campaigns` and `/growth/email/sequences` return **real data** (campaigns and sequences exist and persist). What cannot be verified is **delivery**. The code path is real; the transport is absent.

### Push / Firebase
`/growth/push/campaigns` and `/growth/push/triggers` return real data. `/push/readiness` honestly reports `pushReady:false`. Campaign management works; delivery is unverifiable.

### GitHub — 12 files
Blocks repo integrations under `/integrations/*` and parts of `/coding/*`. Note `/integrations/*` is **also** operator-tier gated (403 for normal users), so this is a second-order blocker.

### Stripe
Razorpay **is** provisioned, so billing is not fully blocked — only the Stripe path.

### Anthropic — 18 files, the widest reference surface
OpenAI and Groq are provisioned, so AI features are **not** blocked; only Claude-specific routing is unavailable. `smartRouter.cjs` selects among available providers.
