## THE CENTRAL FINDING — Executive OS maintains a second, partially-fabricated revenue number

### W2 — the OTHER dashboard

`GET /eos/v6/dashboard` → **business.mrr: 54051**, a completely different figure from the same
underlying reality, sourced from `executiveState.syncOrgStatus()` → `businessOrgState.getDashboard()`.

### Cross-OS reconciliation table (Step 3)

| Source | Value | Executive Value | Match | Root Cause |
|---|---:|---:|---|---|
| Finance OS (`/revenue/dashboard`) | ₹108,891 MRR | — | — | authoritative |
| `businessOrgState` (`/eos/v6/context`) | — | ₹54,051 MRR | ❌ **No** | **Genuine bug** — a second, independent, partially-synthetic MRR computation feeds the executive layer instead of the real Finance OS figure |

This is **not** different scope, a different time window, intentional aggregation, or a stale
cache — it is a structurally different computation (`businessOrgState`'s own deal-pipeline model,
seeded partly by an autonomous demo simulation) reporting under the same "MRR" label the founder
would reasonably expect to be the real number.

### Root cause — traced to source

`backend/services/businessOrgState.cjs`'s own code comment (written in a prior pass) already
documents the mechanism:
```js
// Zero-Trust Competitor Remediation, Phase 2: this dashboard previously
// reported revenue/lead counts with zero disclosure that some deals
// originate from businessOrg.cjs's autonomous demo tick (fictional
// company names, Math.random() values, a setTimeout auto-advance
// cascade...) — a real consumer of this data ... had no way to
// distinguish simulated activity from real customer activity.
```
That fix added a `dataIntegrity` field to `businessOrgState.getDashboard()`'s own response.
**`executiveState.syncOrgStatus()` read only `d?.revenue?.mrr` and dropped `dataIntegrity`
entirely** — reintroducing the exact disclosure gap the source had already fixed for itself, one
layer up.

### Measured contamination

```js
const s = require('./backend/services/businessOrgState.cjs');
const d = s.getDashboard();
// d.revenue.mrr = 54051
// d.dataIntegrity = {
//   totalDeals: 1079, syntheticDeals: 211, realDeals: 868,
//   note: "211 of 1079 deals in this dashboard were generated by the
//          autonomous demo simulation (businessOrg.cjs's growth/CRM
//          tick), not real customer activity."
// }
```
**19.6% of the deals feeding the executive-visible MRR are synthetic**, with zero indication of
that at the layer a founder actually reads.

### Fix + negative test

`syncOrgStatus()` now passes `dataIntegrity` through unchanged; the number itself was not altered.
```js
// before
ctx.orgStatus.business = { mrr: d?.revenue?.mrr, winRate: d?.pipeline?.winRate, deals: d?.pipeline?.total };
// after
ctx.orgStatus.business = {
  mrr: d?.revenue?.mrr, winRate: d?.pipeline?.winRate, deals: d?.pipeline?.total,
  dataIntegrity: d?.dataIntegrity || null,
};
```
```
disclosure now reaches executive layer: true
synthetic ratio visible: 211/1079
```
Graceful-degradation preserved — when `businessOrgState` throws, `ctx.orgStatus.business` is
`undefined` exactly as before (verified: no crash, no change to the error path).

### Why the number itself was not repointed to Finance OS

`_bizSt()` (business org state) is also consumed by `executiveOrg.cjs`'s and
`executiveWorkflow.cjs`'s own department-tick logic — repointing the dashboard's MRR source to
Finance OS's `revenueOS.cjs` would only fix the display, while the underlying tick behavior these
20 department agents run on would remain unchanged and still diverge from it. That is a broader
architectural decision than a "smallest existing implementation" display fix, and outside this
pass's fix policy (P0/P1 only, prefer minimal correction, do not modify unrelated OS
implementations). Documented as a genuine gap with the full reconciliation table above.

## DEFECT — Mission count divergence (investigated, NOT fabrication)

`GET /eos/v6/dashboard` → `missions.total: 9,263` vs. real Mission OS `/mission/runtime/status` →
`total: 2,130`.

### Investigation (per Step 3's instruction not to immediately call a discrepancy a bug)

```js
const st = require('./backend/services/executiveState.cjs');
const list = st.listExecMissions({ limit: 99999 });
// total: 9,263
// linked to real orchestrator (orchMissionId present): 8,290 (89.6%)
```
89.6% of `execMissions` carry a genuine `orchMissionId` pointing at a real Mission OS orchestrator
record. This is a **different aggregation window** — `executiveState`'s own tracking array grows
every time an executive department creates or observes a mission (via `_mission()` in
`executiveOrg.cjs`), independent of Mission OS's own bounded orchestrator snapshot
(`orchestrator-state.json`, capped at ~17 live+recent records by design; `missions.json` is the
2,130-record authoritative store).

**Not fabrication** — verified no synthetic mission titles or fake IDs. **Is a genuine gap**: no
retention cap exists on `execMissions`, and `byStatus` shows `active: 9,259 / completed: 4` —
almost every record is stuck `active`, strongly suggesting stale accumulation rather than a
faithfully-maintained live count. File size: 6,058,053 bytes. Documented, not fixed — see
Capability Matrix §9 for rationale (shared-infrastructure risk, same as prior "not fixed" findings
in Finance/Developer/Memory/Mission OS passes).

## Health-score honesty (Step 7)

### W3 — before the fix

```js
try {
  const d = _engSt()?.getDashboard() || {};
  ...
} catch { health.orgs.engineering = { score: 50 }; }

```

```
  overall score: 85                       <- computed AS IF engineering were healthy-ish
```

### Fix + negative test

Every fallback branch now also sets `unavailable: true`, and a top-level `unavailableSources`
array is computed:
```

  unavailableSources: ["engineering"]
  overall score (still numeric, but flagged): 85

T2 all sources healthy:
  unavailableSources: []
  overall score: 85
```
The numeric `score` field is unchanged (existing consumers keep working), but a caller can now
distinguish "computed from real data" from "one or more sources genuinely down" — which was
previously indistinguishable.
