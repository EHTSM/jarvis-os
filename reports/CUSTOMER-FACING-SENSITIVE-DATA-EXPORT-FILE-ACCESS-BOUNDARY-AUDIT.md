## Genuine Defects Found and Fixed — 2

### 1. Cross-tenant + operator-bypass file disclosure via `GET /exports/global/:filename` (P1)

The "global" (account-personal, non-org) export scope's entire access control was "the filename is
unguessable" — stated explicitly in the route's own comment, but false for every real generator in this
codebase. All 7 `exportFileService.persist()` callers that use this scope build filenames from
`Date.now()`, a plain date string, or a 4-character non-cryptographic `Math.random()` suffix — never a
real secret:

| Generator | Filename pattern | Content |
|---|---|---|
| `accounts.js` (`/accounts/me/export`) | `gdpr-export-${accountId}-${Date.now()}.json` | Full GDPR account export: profile, billing, orgs, CRM, assets |
| `founderJournal.js` (`/fop/report/export`, operator-only at generation) | `fop-report-${date}.docx\|pptx` | Founder Operating Report — zero entropy, pure date |
| `graph.js` (`/graph/export`, operator-only at generation) | `knowledge-graph-export-${Date.now()}.json` | Full knowledge-graph dump |
| `companyFactory.js` | `blueprint-${bp.id}.json` (`bp.id` = timestamp + 4 base-36 chars) | Company blueprint |
| `apiDocs.js` (×2, operator-only at generation) | `openapi-${Date.now()}.json`, `postman-collection-${Date.now()}.json` | API surface docs |
| `codingAssistant.js` | `patch-${crypto.randomUUID()}.zip` | Real UUID — not guessable, but retrieval still had no ownership check |

**Live-reproduced (two fresh ordinary customer accounts, real HTTP requests, no fabricated
credentials):**
- Customer B brute-forced Customer A's exact GDPR-export filename in 3,025 attempts (millisecond
  timestamp search around a roughly-known trigger time) and downloaded A's full GDPR export
  (profile, billing, org data) — `200 OK`.
- Separately, and more critically: Customer B fetched Customer A's export by its *exact* filename with
  zero brute force needed once the filename is known by any means (referrer leak, browser history,
  shared support ticket, etc.) — `200 OK`, no ownership check at all.
- A real, pre-existing operator-only founder report (`fop-report-2026-08-13.docx`, generated by the
  operator days earlier, found on disk) was downloaded by an ordinary `role:"user"` customer using
  **zero brute force** — just the predictable date-only filename. This is a full bypass of the
  `operatorOnly` gate that protects the report's *generation* route, achieved purely through the
  unguarded retrieval route.

**Fixed** by reusing the exact ownership-check mechanism already certified for
`/creative/image|video/file/:filename` in `creativeStudio.js` (`_fileOwnedOrDenied()`, comparing the
caller's `accountId` against the `accountId` `creativeAssetLibrary.cjs` already records for every
`persist()`ed file via `storeAsset()`, looked up by `getAssetByUrl()`) — no new authorization mechanism.
One deliberate deviation from that precedent: **this route fails CLOSED, not open, when no matching
record is found** — live-testing found real pre-existing files (`fop-report-2026-08-13.docx`) that
predate a later addition of the `url` field to the asset-library's fast-lookup index and so have no
matching record; failing open on a lookup miss would have left exactly this bypass in place. A second,
unrelated bug was found and fixed in the same pass: the shared `_serve()` handler read
`req.params.orgScope`, which does not exist on the `/exports/global/:filename` route (only `:filename`
is a named param there) — the first fix attempt silently no-opped because of this, caught by re-running
the same live reproduction against the "fixed" code and seeing it still succeed.

**Live-verified post-fix**: attacker `404`, real owner `200` (own file only), legacy unindexed founder
report `404` (previously the ordinary-customer bypass — now closed), nonexistent filename `404`
(baseline behavior unchanged). Org-scoped `/exports/:orgScope/:filename` (already gated by
`requireOrgMember`) reconfirmed unaffected by this change.

### 2. Path traversal in `GET /odi/dom/:filename` (P1)

`domAnalyzerService.cjs`'s `getAnalysis(filename)` joined the caller-supplied `:filename` directly into
`DOM_DIR` with **zero sanitization** — no regex allowlist, no `path.basename()`, no containment check.
The route itself (`odi.js:139`) is gated only by `requireAuth` (not operator-only, not per-file
ownership — DOM analyses are a single shared store).

**Live-reproduced**: an ordinary authenticated customer requested
`GET /odi/dom/..%2F..%2F..%2Fpackage.json` and received the repository's real `package.json` content —
confirmed a genuine path traversal, not merely theoretical. Exploitability is bounded to files that
parse as valid JSON (the handler `JSON.parse()`s the result), which narrows but does not eliminate real
risk — other JSON data stores on disk could contain sensitive configuration or records.

**Fixed** with the identical `path.basename()` + `startsWith(DIR + path.sep)` containment-check pattern
already established and certified in `exportFileService.cjs`'s `resolveLocal()` — applied at the one
place the unsafe join happens (inside `getAnalysis()`), not duplicated across the route layer.

**Live-verified post-fix**: the same traversal payload now returns `404` with no file content leaked;
a real, legitimately-named DOM analysis file already on disk is still servable normally (`200`).

## Other Items Checked — Confirmed Clean, No Fix Needed

- **`resolveLocal()`'s path-traversal guard** (`exportFileService.cjs`) — already correctly defends via
  regex validation at the route layer plus `path.basename()` + containment check at the service layer
  (defense in depth); this was the pattern reused for both fixes above.
- **`founderVault.js`'s `/vault/export` and `/vault/backup`** — a first-pass grep flagged these as
  possibly unauthenticated; the full file shows `router.use("/vault", requireAuth, operatorOnly)`
  applied once near the top of the file, covering both routes. Content is additionally
  passphrase-encrypted client-side-supplied before being returned (`v.exportVault(passphrase)`,
  `em.generateBackup(passphrase)` — 400 if no passphrase given). Not customer-reachable: no frontend
  code calls either route. **CLEAN** — the initial flag was a false alarm from an incomplete
  single-pass grep, corrected by reading the full file.
- **Frontend consumers**: no frontend code calls `/exports/*`, `/accounts/me/export`, `/vault/export`,
  `/vault/backup`, or `/odi/dom/*` directly with custom handling — all traffic through these surfaces
  that does exist in the frontend goes through the shared `_client.js` fetch wrapper, which checks
  `response.ok`, throws a structured error on failure, and every caller catches it into
  `{ ok: false, error, status }` — no seeded/fake sensitive data is ever displayed on an authorization
  failure.
- **ZIP/CSV export tenant boundaries** (`crm.js`'s `/crm/leads/export`) — already correctly scoped by
  `userId`/orgId unless the caller is an operator; unrelated to this mission's two fixes, confirmed
  unchanged.
- **Signed-URL generation** (`storageService.cjs`'s `signedUrl()`) — 1-hour expiry, AWS SigV4
  query-string signing bound to the exact object key passed in (not broadly valid across the bucket).
  Only two callers exist: `exportFileService.cjs` (inherits this mission's filename-entropy fix when
  cloud storage is configured) and an internal, non-customer-reachable admin diagnostic self-test.
  Mechanism itself is sound; its only real-world exposure was via the filename-entropy gap already
  fixed above.

## Limitations / Lower-Severity Note (P2, Not Fixed This Mission)

**Error-message leakage is a repo-wide pattern, not unique to this scope.** Several file-adjacent routes
(`odi.js`, `apiDocs.js`, `graph.js`, `companyFactory.js`, `founderJournal.js`, `codingAssistant.js`,
`founderVault.js`, and many unrelated routes elsewhere in the codebase) return `e.message`/`err.message`
directly to the client on a 500. Node's `fs` module embeds absolute filesystem paths in its own error
messages (e.g. `ENOENT: no such file or directory, open '/abs/path'`), so a route that lets a raw
filesystem error reach `e.message` can leak a real server path. With this mission's path-traversal fix
in place, `domAnalyzerService.cjs`'s `getAnalysis()` no longer joins arbitrary external paths, so its
own error messages are now bounded to paths inside the fixed, non-secret `DOM_DIR` — meaningfully
lowering severity there specifically. Fixing this pattern everywhere it occurs would mean touching
dozens of already-certified, unrelated routes across the codebase — outside this mission's bounded
scope per its own rules ("do not re-audit already-certified surfaces," "apply the smallest existing-
pattern fix"). Flagged here as a candidate for a future dedicated, narrowly-scoped mission rather than
fixed piecemeal in this one.
