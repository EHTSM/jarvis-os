## Mission

The prior audit fixed a real cross-tenant IDOR in `businessMissionAutomation.cjs`, and along the way
discovered — but explicitly deferred, as out of that audit's authorization-focused scope — a separate,
real reliability defect: every business-automation execution step crashes with `"Cannot read
properties of undefined (reading 'name')"`, for every caller, unconditionally. This mission's task was
to investigate that crash from first principles (not assume the prior diagnosis was complete), find
the true root cause, determine its real blast radius, and fix it using existing architecture.

## Reproduction

Confirmed live, both via direct service-layer calls and real HTTP requests against port 5050, both
before any fix:

```
POST /business/automation/step {"entityType":"lead","stepName":"ingest_lead","entity":{...}}
→ every attempt: "Cannot read properties of undefined (reading 'name')"
```

Confirmed this is **not tenant-specific**: even a lead's own legitimate owner org hit the identical
crash running automation on its own real data. Confirmed **deterministic**: same failure, every time,
regardless of entity content, entity type, or caller.

## Root Cause (confirmed by direct source read, not assumed)

`autonomousExecutionRuntime.cjs`'s `_runAttempt` function — the real code path a registered
capability's handler is invoked through — delivers exactly this shape to the handler:

```js
capHandler.handler({
    input:      rec.input,   // the caller's raw, unparsed string — NOT the parsed object
    missionId:  rec.missionId,
    stageId:    rec.stageId,
    agentId:    rec.assignedAgent,
    policy,
    executionId: rec.executionId,
});
```

There is **no `entity` field, ever** — this is the runtime's real, permanent contract. `rec.input`
itself is set by `_mkRecord` as `(opts.input || "").slice(0, 500)` — truncated to 500 characters.

`businessMissionAutomation.cjs`'s `runTemplate`/`runStep` call `executeStage({input:
JSON.stringify(ctx), ...})`, where `ctx = {entity, entityType, missionId, stepName, input, meta}`. All
27 of that file's capability handlers then do `const { entity } = ctx` on the object the runtime hands
them — but that object's `input` field is a raw string, never `ctx` itself, and no `entity` key exists
on it at all. `entity` is therefore always `undefined`, and `entity.name` (or `.phone`, `.score`,
`.stage`, depending on the handler) throws exactly the observed error.

**Blast radius, confirmed not assumed**: checked the runtime's other real capability consumer,
`engineeringCapabilities.cjs` (27+ handlers, e.g. `code_search`, `patch_apply`, `build`, `test`,
`rollback`). Every one of them correctly treats `ctx.input` as a plain string
(`ctx.input.replace(...)`, `ctx.input?.trim()`) — matching the runtime's real contract exactly.
**`businessMissionAutomation.cjs` is the sole outlier.** This confirms the defect is isolated to one
file's authoring mistake, not a defect in the shared `autonomousExecutionRuntime.cjs` itself — the
runtime's actual contract has always been internally consistent; one caller was simply built against a
different, incorrect assumption.

**A second, compounding defect** that would have blocked even a straightforward "just re-parse
`rec.input`" fix: measured a realistic real lead's `JSON.stringify(ctx)` at 537 characters — already
exceeding the 500-character truncation. Re-parsing the truncated string would throw a JSON syntax
error for nearly every real-world entity, not merely large edge cases.

**Failure classification** (per the mission's explicit checklist): deterministic — yes. Input-specific
— no (every input crashes). Tenant-specific — no (every org, including a record's own owner, crashes
identically). Authentication-related — no. State-related — no. Persistence-related — no.
Concurrency-related — no. This is purely a code-level interface contract mismatch between one caller
and the shared runtime.

## Fix

Reused the existing `registerCapability`/`executeStage` architecture exactly as designed — no
redesign, no new execution engine, no change to `autonomousExecutionRuntime.cjs` itself.

An in-process side-map, keyed by `stageId` (already generated by `businessMissionAutomation.cjs`
itself before each `executeStage()` call), holds the real, untruncated `ctx` object:

```js
const _ctxByStageId = new Map();
function _stashCtx(stageId, ctx) { _ctxByStageId.set(stageId, { ctx, ts: Date.now() }); ... }
function _wrapHandler(realHandler) {
    return async (runtimeCtx) => {
        const stashed = _ctxByStageId.get(runtimeCtx.stageId);
        if (!stashed) return _fail(`No business context found for stageId ${runtimeCtx.stageId} — capability invoked outside runTemplate/runStep`, true);
        return realHandler({ ...stashed.ctx, executionId: runtimeCtx.executionId, agentId: runtimeCtx.agentId, policy: runtimeCtx.policy });
    };
}
```

`init()` now registers `{ ...cap, handler: _wrapHandler(cap.handler) }` for each of the 27
capabilities, instead of the raw handler. `runTemplate`/`runStep` call `_stashCtx(stageId, ctx)`
immediately before their `executeStage()` call. Zero changes to any of the 27 individual capability
bodies (beyond the failure-honesty fix below) — the wrapper is the single point of correction.

**A genuine bug in this fix's own first version was found and corrected within the same pass**:
releasing the stash inside the wrapped handler's own `finally{}` block is correct for a single
attempt, but `executeStage` internally retries the **same** `stageId` up to `policy.maxRetries` times
on failure. Live-reproduced during cross-tenant verification: a real cross-org rejection on attempt 1
correctly threw `"Not found: <id>"`, but attempt 2's retry found the stash already deleted and reported
the misleading fallback `"No business context found"` message instead of retrying the real failure.
**Fixed**: moved the release (`_releaseCtx(stageId)`) into `runTemplate`/`runStep`'s own `finally{}`,
after their `executeStage()` call fully resolves (all attempts), not per-attempt inside the handler.

## Failure Honesty (a second, directly-related defect found and fixed)

Live-verified the fixed runtime end-to-end with a real cross-tenant scenario and found: 6 of the 27
capability handlers — the ones performing the actual CRM mutation (`ingest_lead`, `send_contact`,
`qualify`, `close`, `update_pipeline`, and the two `recordCampaignEvent` marketing handlers) — wrapped
their `businessDataService` call in `try{}catch{}`, falling through to a generic success message on
**any** failure. This pattern pre-dates both this mission and the prior IDOR-fix mission, but was
**invisible until now**: the crash bug prevented these lines from ever executing with real data at
all, so the swallow was structurally unreachable in practice. The moment the crash was fixed, this
became a live, active vulnerability: a real cross-org write attempt correctly threw `"Not found: <id>"`
from `businessDataService`, but the surrounding `try{}catch{}` silently caught it and reported
`"status":"completed"` — **directly undoing the previous mission's own IDOR fix's effective
protection**, since the caller could no longer distinguish "wrote successfully" from "silently blocked."

**Fixed**: removed the swallow from the 6 CRM-mutation call sites, letting a genuine failure propagate
up to `executeStage`'s own existing `try/catch` (which already correctly converts a thrown error into
a real `"failed"` status with the real message — no new error-handling architecture needed).
Deliberately left the genuinely non-critical `_mem()?.recordDecision(...)`/`_alert()?.fire(...)`
bookkeeping calls swallowed where they coexisted in the same handler (e.g. `close`) — these are
best-effort side notes distinct from the actual business mutation being reported to the caller, and
swallowing their failure is not a fake-success concern in the same sense.

## ROOT CAUSE

`autonomousExecutionRuntime.cjs`'s real registered-capability contract delivers
`{input, missionId, stageId, agentId, policy, executionId}` to a handler — `input` is the caller's
raw, 500-char-truncated string, never the parsed structured object. `businessMissionAutomation.cjs`'s
27 handlers all assumed a structured `{entity, entityType, ...}` ctx the runtime never provides — an
authoring mismatch isolated to this one file, confirmed by checking the runtime's other real consumer
(`engineeringCapabilities.cjs`), which correctly uses the real string-based contract and is unaffected.

## BLAST RADIUS

- **Business automation**: 100% of executions, every caller, every org, unconditionally — now fixed.
- **Engineering capabilities** (`engineeringCapabilities.cjs`, 27+ handlers): confirmed unaffected,
  both by code inspection (correct contract usage) and a live post-fix HTTP check.
- **Autonomous missions / other OS workflows**: not affected — this defect was isolated to
  `businessMissionAutomation.cjs`'s own capability registrations; no other file in the codebase
  registers capabilities with the same incorrect `ctx.entity` assumption (confirmed via the same grep
  sweep that found the 2 real consumers of this shared runtime).

## FIXES

- `backend/services/businessMissionAutomation.cjs`: added a `stageId`-keyed side-map
  (`_stashCtx`/`_releaseCtx`) and a handler-wrapping function (`_wrapHandler`), applied at
  registration time in `init()`. `runTemplate`/`runStep` stash the real ctx before calling
  `executeStage()` and release it in a `finally{}` after that call fully resolves.
- Removed the `try{}catch{}` fake-success swallow from 6 CRM-mutation capability handlers
  (`ingest_lead`, `send_contact`, `qualify`, `close`, `update_pipeline`, 2× campaign-event handlers),
  letting real failures propagate to the runtime's own existing, correct error-handling.
- 5 new regression tests, each independently negative-tested.
