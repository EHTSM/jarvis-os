## Verdict up front

**Screen-reader certification is NOT AWARDED.** No screen reader was
successfully driven through a single Ooplix journey. Every environment was
either unavailable, unsafe to use, or technically incapable of hosting the
test.

What *was* achieved: the real **computed accessibility tree** — the same tree
AT-SPI / UIA / NSAccessibility are populated from — was measured across 7
surfaces in both themes, and one new contrast defect was found and fixed. That
is genuine accessibility evidence, but it is **not** screen-reader evidence,
and it is not reported as such.

### Incident — VoiceOver was started on the operator's live machine

While probing for scriptability, `osascript -e 'tell application "VoiceOver" to
return version'` **launched VoiceOver** on the operator's desktop (pid 85927,
00:00:19). `tell application` launches the target app; a screen reader taking
over a live desktop is a disruptive, outward-facing action that should have
been confirmed first. It ran roughly one minute and was terminated.

Host state verified clean afterwards:
```
VoiceOver confirmed off
com.apple.universalaccess voiceOverOnOffKey = 0   (unchanged)
```

The operator was then asked how to proceed and chose **Android emulator only**.
macOS VoiceOver is therefore recorded **BLOCKED**, not "not available" — it
exists and works, but was deliberately not used on a live desktop.

### TalkBack — genuinely reached, then blocked

This got further than any other environment and is worth recording precisely.

**What worked.** A `Pixel_7_API_34` AVD booted (Android 14).
`com.google.android.marvin.talkback` was installed, enabled, and confirmed
**bound as a live service** — not simulated:

```
Bound services:{Service[label=TalkBack,
  feedbackType[FEEDBACK_SPOKEN, FEEDBACK_HAPTIC, FEEDBACK_AUDIBLE],
  capabilities=251, eventTypes=TYPES_ALL_MASK]}
talkback pid: 13910
```

Its own onboarding surface was captured through the accessibility tree,
proving the service was actually running:

```
TextView   "TalkBack is on"
TextView   "Welcome to TalkBack"      "Page 1 of 7"
Button     "Finish"   content-desc="Finish tutorial"
```

**Why it still failed.** The AVD is an **XR / desktop-mode image**
(`xrDesktopMode`, `com.android.systemui.xrhomeenv`,
`SysUiVisibilityBarrier`). On that image `uiautomator dump` returns
`ERROR: null root node returned by UiTestAutomationBridge` **deterministically
whenever Chrome renders** — confirmed on three consecutive attempts — while
working on system UI. TalkBack also repeatedly dropped from `Bound` to
unbound. Without a readable node tree over the web content, no journey could be
driven or evidenced.

Per the brief's stop condition — *"Stop if environment becomes unstable"* — the
emulator was shut down cleanly rather than pushed further.

### Live region — investigated, not a defect
The `alert` region appeared in dark but not light, with an empty AX `name`.
Traced to `TrialBanner.jsx`, which returns `null` unless a billing tier is
active (`if (!tier || dismissed) return null`) — it was dismissed in the light
run. Verified it carries real announceable text:

```
{"cls":"trial-banner trial-banner--critical","live":"polite",
 "text":"Trial expires today Automations will pause at midnight…"}
```

The empty AX name is expected — the text lives in descendants, which screen
readers read. **No finding raised.**

## Phase 4 — G1-B193, re-measured against the real accessibility tree

**The gap is NOT closed, and axe's acceptance of a placeholder was not used as
proof.**

Of the form controls actually rendered across the measured surfaces:

| Name source | Count | WCAG standing |
| --- | ---: | --- |
| Visible `<label>` | **1** | Satisfies 3.3.2 |
| `aria-labelledby` | 0 | Would satisfy 4.1.2, not 3.3.2 |
| `aria-label` | **4** | Satisfies 4.1.2 (accessible name) — **not** 3.3.2 |
| `title` only | 0 | Weak |
| **`placeholder` only** | **8** | **Fails 3.3.2** — the label vanishes on input |
| Genuinely unnamed | **0** | — |

The four `aria-label` controls are named correctly for a screen reader:
`"Task or command input"`, `"Select AI model"`, `"Command search"`.

The eight placeholder-only controls (`.cv2-search`, `.pv2-input` ×4,
`.pv2-textarea`, `.chat-input` ×2) **do** get an accessible name from the
placeholder, which is why axe reports zero. They still fail WCAG 3.3.2, because
the visible label disappears the moment the user types.

**Distinction, stated plainly:**
- *WCAG-compliant accessible name (4.1.2)*: **satisfied** — 0 unnamed controls.
- *Persistent visible label (3.3.2)*: **not satisfied** — 8 of 13 rendered
  controls rely on a disappearing placeholder.

Full static scope is unchanged: **763 findings** (518 `FORM-PLACEHOLDER-ONLY`,
245 `FORM-UNLABELED`). Closing it means authoring ~763 pieces of UX copy across
ten product families — **content authoring and design, not accessibility
recovery.** Classified honestly rather than invented.

**G1-B193 status: OPEN — GENUINE CAPABILITY GAP.**

## Phase 5 — G2-B195, re-tested

**Structure is functionally valid; the automated rule still fires. Not
modified to obtain a green result.**

Accessibility tree with the palette open:

```
dialog: 1   combobox: 2   listbox: 1   option: 98   group: 11   button: 125
unnamed interactive: 0
aria-activedescendant: {"activedescendant":"cp-opt-10","resolves":true,
                        "selected":"true","text":"⬡Execution Engine"}
```

Everything a screen reader needs is present: the dialog is named and modal, the
listbox is named, options carry `aria-selected`, groups are labelled, and
`aria-activedescendant` resolves to a real selected option as the user arrows.

`aria-required-children` still fires because the hover-revealed pin buttons are
`<button>` children of the `listbox`. B.19.5 tested **all four** candidate
structures against axe; only hoisting the pins outside the listbox conforms,
which requires restructuring the palette DOM and layout.

**Assessment:** *recoverable only with UX/DOM redesign* — a **genuine
design-system gap**, not a quick fix. Practical AT impact is limited: the pin
button is `opacity: 0`, mouse-only, and absent from the arrow-key model.

**G2-B195 status: OPEN — GENUINE DESIGN-SYSTEM GAP.**

## Phase 6 — Fix applied

### New finding: ErrorBoundary fails contrast in light theme
**FIXED.** The ErrorBoundary only renders when a panel actually crashes, so
B.19.5's sweep never reached it. Measured live:

| Element | Colour | Ratio | Required |
| --- | --- | ---: | ---: |
| `.eb-subtitle` | `rgba(248,113,113,0.85)` on `rgb(244,234,237)` | **2.09:1** | 4.5 |
| `<strong>` (inherits) | same | **2.09:1** | 4.5 |
| `.eb-btn--primary` | `--danger` on its own danger tint | **3.93:1** | 4.5 |

Same defect class B.19.5 fixed elsewhere: a hardcoded dark-mode red, and danger
text on a danger tint. Both pointed at the existing `--on-danger-tint` token.
Dark unchanged (it aliases to `--danger` there).

**Re-verified live:** light contrast **3 → 0**.

No mass codemod was applied; two rules were changed after tracing the actual
computed colours.

## Certification verdict

> **NOT CERTIFIED for screen-reader accessibility.**
>
> Ooplix holds strong, independently re-verified automated accessibility:
> zero AA violations, zero contrast failures in both themes, full keyboard
> operability, correct dialog semantics, and zero unnamed interactive nodes in
> the real computed accessibility tree.
>
> **Screen-reader certification remains unearned.** Not one of the five
> required screen readers was driven through an Ooplix journey. macOS VoiceOver
> was BLOCKED as unsafe on a live desktop; TalkBack was genuinely running but
> its host image could not expose the web content's node tree; NVDA, Narrator
> and iOS VoiceOver were NOT AVAILABLE on this platform.
>
> The previous accessibility certification therefore **remains CONDITIONAL**,
> exactly as it was before this phase.

### What would actually close it
1. A standard (non-XR) Android AVD or physical device → TalkBack journeys.
2. A Windows host or VM → NVDA + Narrator.
3. A macOS session the operator has explicitly set aside for VoiceOver.
4. A booted iOS simulator or device → iOS VoiceOver.
